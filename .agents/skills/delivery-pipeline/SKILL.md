# 交付流水线

把交付视为严格有序的八阶段状态机。先读取适用范围内的 `AGENTS.md` 和仓库说明；保留每一阶段的证据。任何阶段失败或停止时，不得跳过门禁继续执行。用户只要求某个后续阶段时，先补齐并展示必要的前置证据。

## 通用状态规则

- 状态依次为：`技术方案 -> 代码开发 -> 单元测试 -> Commit -> 冲突检查 -> Push -> 部署 -> 功能验证`。
- 只有当前阶段满足成功条件后才能进入下一阶段。
- 将命令、关键输出、文件或 commit 作为证据；不得只声称“已完成”。
- Commit、Push、部署是三个独立确认门禁；一次确认不得授权后续门禁。生产部署始终单独确认。
- 失败时记录当前状态、停止原因、已完成证据和恢复条件。

## 1. 技术方案

- 进入条件：已确认用户目标和仓库上下文。
- 执行：明确范围与非目标、现有实现、方案、验收标准、风险、依赖和回滚方式；缺少会实质改变方案的信息时询问用户。
- 成功证据：可执行的方案及逐项可验证的验收标准。
- 停止条件：目标或验收标准不明确、关键权限或依赖缺失、风险不可接受。

## 2. 代码开发

- 进入条件：技术方案可执行。
- 执行：按现有架构完成最小必要改动，不改无关文件；遵守适用的语言和框架规范。
- 成功证据：任务相关 diff 与修改文件清单能够映射到方案。
- 停止条件：发现方案假设错误、范围显著扩大、用户改动冲突或无法安全继续。

## 3. 单元测试

- 进入条件：代码改动完成且可测试。
- 执行：补充正常、边界和异常路径；先运行相关单元测试，再运行仓库要求的完整检查。
- 成功证据：测试用例清单、执行命令、退出状态和结果摘要。
- 停止条件：任何测试或检查失败、测试无法可靠执行。禁止进入 Commit、Push 或部署。

## 4. Commit

- 进入条件：所有要求的测试与检查通过。
- 执行：展示工作区状态、任务相关 diff、测试结果、仅属于当前任务的拟暂存文件，以及符合 Conventional Commits 的拟用提交信息；请求明确确认后才暂存并提交。
- 成功证据：新 commit 哈希、提交信息和实际提交文件。
- 停止条件：用户未确认、包含无关文件、工作区在确认后变化或 commit 失败。

## 5. 冲突检查

- 进入条件：存在已确认的本地 commit，且已知远端与目标分支。
- 执行：执行 fetch；比较本地分支和 upstream 的领先、落后、分叉状态。发现远端分歧或冲突时立即停止，列出分支状态与冲突文件，由用户选择 merge 或 rebase；解决后重新运行单元测试和完整检查。
- 成功证据：fetch 结果、upstream、领先/落后计数，以及无冲突结论。
- 停止条件：无 upstream、fetch 失败、远端落后/分叉、存在冲突或用户尚未选择策略。

## 6. Push

- 进入条件：冲突检查通过，且提交后的验证结果仍有效。
- 执行：展示分支、upstream、待推送 commit 和最新测试结果；请求独立明确确认后执行普通 push。
- 成功证据：push 命令结果和远端分支/commit；禁止 force push。
- 停止条件：用户未确认、远端状态变化、push 被拒绝或验证已失效。

## 7. 部署

- 进入条件：Push 成功，且仓库中有可靠部署文档、脚本或配置依据。
- 执行：读取部署依据，展示目标环境、精确命令、版本、风险、观测方式和回滚方法；请求独立明确确认后执行。生产环境必须再次以“生产部署”语义明确确认。
- 成功证据：部署命令结果、版本/制品、目标环境和平台返回状态。
- 停止条件：缺少可靠说明、环境或版本不明确、用户未确认、部署失败。不得猜测命令。

## 8. 功能验证

- 进入条件：部署成功，或用户明确指定可验证的已运行环境。
- 执行：逐项依据技术方案的验收标准检查适用的健康状态、接口、页面或日志；避免产生非必要业务数据。
- 成功证据：每项验收标准的通过/失败、验证方法和观察结果。
- 停止条件：任何验收失败、环境不可访问或证据不足；报告影响和安全的回滚/修复选项，不把失败标记为完成。

## 输出交接

报告最终状态、各阶段证据、未完成项、风险和下一项需要用户确认的动作。若流程停止，明确从哪个阶段以及满足什么条件后恢复。
