# 交付流水线

把交付视为严格有序的十一阶段状态机。先读取适用范围内的 `AGENTS.md` 和仓库说明；保留每一阶段的证据。任何阶段失败或停止时，不得跳过门禁继续执行。用户只要求某个后续阶段时，先补齐并展示必要的前置证据。

本 Skill 是交付阶段、证据、停止条件和确认门禁的唯一来源。外部协作 Skill 可以在既有阶段内部增加角色分工、审核或实现子流程，但必须先完整读取本 Skill，不得复制出第二套状态机，不得改变阶段顺序，也不得削弱或替代本 Skill 的任何门禁。

## 通用状态规则

- 状态依次为：`技术方案 -> 分支准备 -> 技术方案归档 -> 代码开发 -> 单元测试 -> Commit -> 远程 main 合并与冲突检查 -> Push -> 部署 -> 功能验证 -> 合并 main`。
- 只有当前阶段满足成功条件后才能进入下一阶段。
- 将命令、关键输出、文件或 commit 作为证据；不得只声称“已完成”。
- 唯一人工确认门禁位于代码开发完成且生产代码 CR 通过之后、单元测试之前。Codex 展示完整任务 diff、生产代码文件、架构对应关系、CR 结果、测试计划和后续交付计划，请用户查看并确认代码。
- 代码查看确认同时授权在计划和范围不变时自动连续执行单元测试、Commit、远程 `main` 合并、Push、部署、功能验证和合并 `main`，后续阶段不得重复请求确认，包括生产部署。若用户只要求执行一个独立后续阶段，则其明确执行请求视为该阶段授权，无需再次确认。
- 代码查看后生产代码、架构、文件范围、部署目标或关键命令发生变化时，授权失效并回到代码查看门禁；仅测试代码按已确认生产契约修正且未改变生产代码时，无需重复确认。远端变化、冲突、验证失败或依据缺失按对应停止条件处理，不以重复确认代替问题解决。
- 失败时记录当前状态、停止原因、已完成证据和恢复条件。

## 1. 技术方案

- 进入条件：已确认用户目标和仓库上下文。
- 执行：明确范围与非目标、现有实现、方案、验收标准、风险、依赖和回滚方式；缺少会实质改变方案的信息时询问用户。
- 成功证据：可执行的方案及逐项可验证的验收标准。
- 停止条件：目标或验收标准不明确、关键权限或依赖缺失、风险不可接受。

## 2. 分支准备

- 进入条件：技术方案可执行，当前目录是 Git 仓库，已确认远端存在 `main`，工作区没有来源不明或未处理的改动。
- 执行：先 fetch 远端并将本地 `main` 同步到 `origin/main`；只以最新 `main` 为基础创建并切换到当前任务的独立分支，不得从其他任务分支派生。优先使用仓库既有命名规则，否则按任务类型使用 `feature/<slug>`、`fix/<slug>`、`docs/<slug>`、`refactor/<slug>` 或 `chore/<slug>`。若用户已切换到明确属于当前任务的独立分支，核验其 merge-base 为任务开始时的 `origin/main` 后才可复用。
- 成功证据：`origin/main` commit、任务分支与 `main` 的 merge-base、任务分支名称、当前分支和干净的起始工作区状态；不得直接在 `main` 上开发。
- 停止条件：不是 Git 仓库、远端 `main` 不存在或状态不明确、工作区存在未处理改动、`main` 落后/分叉、任务分支不是从所要求的 `main` 基准派生、目标分支用途不明、创建或切换失败。

## 3. 技术方案归档

- 进入条件：技术方案可执行，分支准备完成，已取得当前聊天名称和技术方案名称。
- 执行：在代码开发前，使用飞书用户身份把第 1 阶段已确认的技术方案正文原封不动地创建为飞书云文档，并写入文件夹 `https://my.feishu.cn/drive/folder/NhkdfHqfdloniYdNuTycU7sRndd`（folder token：`NhkdfHqfdloniYdNuTycU7sRndd`）。文档标题严格使用 `<技术方案所在的聊天名称>之<技术方案名称>`，不添加额外前后缀。正文必须完整保留原方案的全部标题、段落、列表、表格、代码块、图示、验收标准、风险、依赖和回滚内容，且顺序一致；禁止摘要、删减、润色、改写、重排或用提纲替代原文，仅允许为适配飞书文档格式进行不改变内容与顺序的格式转换。创建后回查文档标题、完整正文和所在文件夹，并将回查内容与原方案逐项核对；发现不一致时立即修正并重新回查。若本次开发新增可访问网页或链接，再使用飞书用户身份在文档 `https://my.feishu.cn/docx/CKI0dwkE4omQbdxkQAMcIkvNn8e` 的现有表格中为每个网页或链接新增一行，严格按 `链接`、`功能`、`启动方式`、`所在目录`、`所在服务器` 五列填写；未知字段填写“待确认”，不得猜测、合并多个链接或省略记录。写入后回查新增行并与技术方案逐项核对。
- 成功证据：实际文档标题、文档 URL、目标文件夹，以及原方案与飞书正文完整一致的核对结果；涉及新增网页或链接时，还需提供链接登记文档 URL、新增行及五列字段与方案一致的回查结果。将技术方案文档 URL 作为后续开发和验收的方案依据。
- 停止条件：聊天名称或技术方案名称无法确定、飞书 CLI 未安装或未登录、目标文件夹或链接登记文档无访问权限、创建或回查失败，正文存在任何缺失、摘要、改写、顺序变化或其他不一致，或者应登记的网页或链接未逐项记录、字段与方案不一致。不得因此省略归档、链接登记或进入代码开发。

## 4. 代码开发

- 进入条件：技术方案可执行，分支准备和技术方案归档完成，当前位于本任务的独立分支。
- 执行：按现有架构完成最小必要改动，不改无关文件；遵守适用的语言和框架规范。生产代码完成并通过 CR 后，展示完整任务 diff、生产代码文件、架构对应关系、CR 结论、测试计划，以及 Commit、主干合并、Push、部署、验证和合并 `main` 的后续计划，请用户查看代码并取得唯一一次明确确认。
- 成功证据：任务分支名称、任务相关 diff 与修改文件清单能够映射到方案，CR 结果，以及用户已查看并确认生产代码和后续计划。
- 停止条件：仍在 `main`、发现方案假设错误、范围显著扩大、用户改动冲突、代码 CR 未通过、用户未确认代码或无法安全继续。

## 5. 单元测试

- 进入条件：代码改动完成且可测试。
- 执行：补充正常、边界和异常路径；先运行相关单元测试，再运行仓库要求的完整检查。
- 成功证据：测试用例清单、执行命令、退出状态和结果摘要。
- 停止条件：任何测试或检查失败、测试无法可靠执行。禁止进入 Commit、Push 或部署。

## 6. Commit

- 进入条件：所有要求的测试与检查通过。
- 执行：核对工作区状态、任务相关 diff、测试结果和仅属于当前任务的拟暂存文件，使用代码查看阶段已展示的 Conventional Commits 提交信息自动暂存并提交，不再请求确认。
- 成功证据：新 commit 哈希、提交信息和实际提交文件。
- 停止条件：缺少有效代码查看授权、包含无关文件、生产代码或计划在确认后变化、测试失效或 commit 失败。

## 7. 远程 main 合并与冲突检查

- 进入条件：存在已确认的本地 commit，当前位于开发分支，且已知 upstream、`origin/main` 和部署目标。
- 执行：部署前先执行 fetch，比较当前开发分支、upstream 与 `origin/main`。把最新 `origin/main` 以 merge 方式合入当前开发分支，不得用 rebase 替代；即使已经包含最新主干，也要以 merge-base/祖先关系给出无须新增 commit 的证据。授权与计划仍有效时自动合并，不再请求确认。发现冲突时立即停止并列出冲突文件。合并产生生产代码变化后重新运行相关单元测试和完整检查，并回到代码查看门禁；只产生不改变代码树的合并 commit 时可自动提交并继续。
- 成功证据：fetch 结果、`origin/main` commit、合并命令与结果、merge-base/祖先关系、冲突状态，以及合并后单元测试和完整检查结果；证明待推送开发分支已包含最新远程主干。
- 停止条件：无 upstream、`origin/main` 不存在、fetch 失败、缺少有效代码查看授权、远端或范围超出已确认计划、存在冲突、合并失败，或者合并后的测试或检查失败。远程主干未合入时禁止进入 Push 和部署。

## 8. Push

- 进入条件：远程 `main` 合并与冲突检查通过，且合并后的测试与检查结果仍有效。
- 执行：核对分支、upstream、已合入的 `origin/main` commit、待推送 commit 和合并后的最新测试结果；与代码查看计划一致时自动执行普通 push，不再请求确认。
- 成功证据：push 命令结果和远端分支/commit；禁止 force push。
- 停止条件：缺少有效代码查看授权、远端状态变化、push 被拒绝或验证失效。

## 9. 部署

- 进入条件：包含最新 `origin/main` 的开发分支已 Push 成功，且仓库中有可靠部署文档、脚本或配置依据。
- 执行：读取部署依据，核对目标环境、精确命令、版本、风险、观测方式和回滚方法；与代码查看阶段的后续计划一致时自动执行，生产环境也不再单独请求确认。
- 成功证据：部署命令结果、版本/制品、目标环境和平台返回状态。
- 停止条件：远程主干未合入、合入后的测试或 Push 未完成、缺少有效代码查看授权、缺少可靠说明、环境或版本不明确、目标或命令超出已确认计划、部署失败。不得猜测命令。

## 10. 功能验证

- 进入条件：部署成功，或用户明确指定可验证的已运行环境。
- 执行：逐项依据技术方案的验收标准检查适用的健康状态、接口、页面或日志；避免产生非必要业务数据。
- 成功证据：每项验收标准的通过/失败、验证方法和观察结果。
- 停止条件：任何验收失败、环境不可访问或证据不足；报告影响和安全的回滚/修复选项，不把失败标记为完成。

## 11. 合并 main

- 进入条件：部署和功能验证均通过，已确认受测版本对应来源分支的待合并 commit，且仓库的 `main` 合并方式与保护规则明确。
- 执行：先 fetch 并确认 `origin/main` 自功能验证后未发生未处理变化；核对来源分支、目标 `main`、待合并 commit、测试与功能验证结果、代码查看阶段已列明的 PR 或本地合并方式、合并后推送动作及回滚方案，一致时按仓库规定自动完成合并。受保护分支必须走 PR，不得绕过保护规则；禁止 force push。
- 成功证据：PR/合并记录、`main` 上包含已验证 commit 的可追溯关系、合并结果及远端 `origin/main` commit。
- 停止条件：缺少有效代码查看授权、`main` 远端变化、合并策略或保护规则不明确、存在冲突、受测 commit 与待合并 commit 不一致、合并或推送失败。若解决冲突或合并结果改变代码树，必须回到代码查看门禁，并重新运行单元测试、完整检查、部署和功能验证后再合并。

## 输出交接

报告最终状态、各阶段证据、未完成项、风险和下一项需要用户确认的动作。若流程停止，明确从哪个阶段以及满足什么条件后恢复。
